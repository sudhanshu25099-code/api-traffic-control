1. Executive Summary

Modern cloud API infrastructures expose critical services to unpredictable, concurrent user traffic. Without deterministic traffic governance, burst floods and malicious spikes lead to server saturation, cascading timeouts, and denial-of-service (DoS) conditions. Standard rate-limiting implementations frequently fail due to two architectural pitfalls:

  • The In-Process Concurrency Trap: Local memory counters in Python coroutines suffer from race conditions under high concurrent volume, permitting 60% to 100% excess traffic beyond configured limits (collapsing entirely during simultaneous bursts).
  • Relational Row Lock Bottlenecks: Maintaining per-request counters in relational databases using SELECT ... FOR UPDATE serializes incoming requests, creating massive lock contention and severely degrading throughput.

API Traffic Control resolves this challenge by strictly decoupling policy persistence from transient state execution. Access policies (tenant identities, tier capacities, algorithms, and replenishment rates) are stored relationally in PostgreSQL. Transient token counters are maintained and evaluated atomically inside Redis using custom pre-compiled Lua scripts (EVALSHA). Intercepted at line-speed by a pure Starlette ASGI middleware, the architecture guarantees strict mathematical compliance, sub-millisecond execution latency, and zero caching staleness.

2. Architectural Decoupling: Policy vs. State

The core architectural innovation lies in isolating transactional metadata from volatile counters. Relational databases excel at relational queries and administrative ACID transactions, while in-memory stores excel at high-frequency atomic decrements.

Architectural Rule: Zero Counter State in Relational Storage
PostgreSQL is queried solely for tenant access rules via a unique indexed lookup (~1.5ms). It is never used to write or update counters. Transient state is exclusively mutated within Redis via Lua in ~0.8ms, guaranteeing high-concurrency scalability without row lock contention.

3. Algorithmic Landscape & Theoretical Grounding (Saleem, 2026)

Our system design is formally grounded in the comparative evaluation published by Umair Saleem (2026) in "A Comparative Survey of API Rate-Limiting Algorithms: Token Bucket, Leaky Bucket, and Sliding Window". Saleem surveyed five foundational algorithms across synthetic Poisson traffic traces (1,057 requests over 100 seconds with artificial bursts at 40 req/s and 60 req/s).

3.3. Key Findings from Saleem (2026) Applied to Our Engine

  • Decision Equivalence: Token Bucket and Leaky Bucket produce identical accept/reject decisions when deployed purely as admission filters. The leaky bucket's water level and the token bucket's depleted capacity are mathematical duals.
  • Superior Burst Accommodation: Token Bucket accepted the largest proportion of total traffic (79.8%) and absorbed both burst spikes (69 and 38 requests) by utilizing accumulated capacity while preserving long-term rate constraints.
  • The Sliding Window Trade-off: While Sliding Window Log enforces an exact ceiling (never exceeding 10 req/s), it achieves the lowest acceptance rate (67.9%) and demands unbounded $O(n)$ memory overhead, making it susceptible to memory exhaustion during DDoS attacks.

4. Algorithmic Mechanics & Mathematical Formulations

Our system implements both Fixed Window Counter and Token Bucket, each authored in Python (as in-process baseline) and in optimized Lua scripts compiled into Redis.

4.1. Fixed Window Counter Model

Time is partitioned into discrete intervals $[k \cdot W, (k+1) \cdot W)$. A scalar counter tracks requests within the current interval:

$$\text{count}(t) = \sum_{i=1}^{M} \mathbf{1}_{\left[\lfloor t/W \rfloor W, \; t\right]}(t_i)$$

Redis Lua Formulation (fixed_window.lua): 

local current = redis.call("INCR", KEYS[1])
if current == 1 then
    redis.call("EXPIRE", KEYS[1], window)
end
if current > capacity then
    return {0, 0, reset_at, capacity} -- Rejected (HTTP 429)
end
return {1, capacity - current, reset_at, capacity} -- Allowed (HTTP 200)

The $2\times$ Boundary Burst Artifact: A client with quota $C=5$ can transmit 5 requests at $t = W - \epsilon$ and 5 requests at $t = W + \epsilon$. Both bursts are accepted, admitting $2C = 10$ requests within a span of $2\epsilon$ seconds.

4.2. Token Bucket Continuous Model

A container of maximum capacity $C$ continuously accumulates tokens at rate $r$. Each request consumes 1 token. When idle, tokens accumulate up to $C$. When $t_{\text{now}} > t_{\text{last}}$, fractional replenishment is evaluated dynamically:

$$\text{tokens}(t) = \min\left(C, \; \text{tokens}(t_{\text{last}}) + (t - t_{\text{last}}) \cdot r\right) - 1$$

Redis Lua Formulation (token_bucket.lua): 

local time_arr = redis.call("TIME")
local now = tonumber(time_arr[1]) + (tonumber(time_arr[2]) / 1000000)
local delta = math.max(0, now - last_updated)
local tokens = math.min(capacity, current_tokens + (delta * refill_rate))

if tokens < 1 then
    return {0, math.floor(tokens), reset_at, capacity} -- Rejected (HTTP 429)
end

redis.call("HMSET", KEYS[1], "tokens", tokens - 1, "last_updated", now)
return {1, math.floor(tokens - 1), reset_at, capacity} -- Allowed (HTTP 200)

Clock Skew Mitigation: Timestamps are obtained directly from the Redis engine via redis.call('TIME'), eliminating discrepancies caused by host clock drift across distributed application nodes.

6. Empirical Benchmarks & Experimental Proof

6.1. The Concurrency Proof: In-Process Failure vs. Atomic Redis Lua

To validate the necessity of Redis Lua execution over in-process memory limiters, we evaluated the system across two distinct experimental paradigms: (1) a single-pass asynchronous unit test in tests/test_algorithms.py, and (2) a multi-trial concurrency burst sweep across increasing parallel batch sizes ($N = 20, 100, 1000$).

A. Single-Pass Unit Test Assertion (tests/test_algorithms.py)

In a single pytest run with 20 asynchronous coroutines targeting a capacity limit of 10, non-deterministic event-loop coroutine interleaving allowed 16 of 20 requests through—a 60% race condition leak:

Execution Substrate Test Scenario (Single Run) Configured Limit Actual Allowed Violation Status
In-Process Python Baseline (InProcessFixedWindow) 20 concurrent coroutines 10 requests 16 requests FAILED (60% Race Leak)
Redis + Atomic Lua (RateLimitMiddleware) 20 concurrent coroutines 10 requests 10 requests PASSED (100% Strict Compliance)

B. Multi-Trial Concurrency Burst Sweep (20 Trials per Size, Limit = 10)

When parallel requests arrive simultaneously without network jitter (via asyncio.gather, simulating an instant burst or retry storm), the non-atomic check-and-increment window in Python degenerates completely, allowing 100% of requests to pass. Theoretical Explanation: In Python asyncio, coroutines interleave execution between reading self.windows.get(...) and incrementing it. As concurrency scales, all requests read the un-incremented counter during the same tick. Redis executes Lua scripts as an isolated, single-threaded transaction, guaranteeing absolute atomicity regardless of arrival density.
